# «ВышКат» — домашнее задание № 1 по КПО

Консольное приложение для учёта парка кикшеринга. Реализация рассчитана на .NET 8 и использует встроенный DI-контейнер `Microsoft.Extensions.DependencyInjection`.

## Возможности

- Приём транспортного средства в парк только после положительного решения `IServiceCenter`.
- Учёт электросамокатов, велосипедов, электровелосипедов, шлемов, зарядных станций и зарядных шкафов.
- Единый список инвентаря с уникальными инвентарными номерами.
- Отчёт по числу транспортных средств, прочих вещей и всех объектов на балансе.
- Подсчёт суточного потребления энергии всеми объектами, реализующими `IEnergyConsumer`.
- Вывод транспорта для новичков по правилу `BeginnerFriendlyScore >= 6`.
- Стартовая демонстрация положительного и отрицательного техосмотра, а затем интерактивное меню.
- Юнит-тесты, в которых `IServiceCenter` заменяется подделкой (`FakeServiceCenter`) через DI.

## Требования

- .NET SDK 8.0 или новее.
- Доступ к NuGet при первом восстановлении пакетов.

## Запуск

Из корня каталога проекта:

```bash
dotnet restore VyshKat.sln
dotnet run --project src/VyshKat.App/VyshKat.App.csproj
```

При старте приложение добавляет демонстрационные данные и показывает отчёты. После этого можно воспользоваться меню: добавить транспорт, добавить вещь, посмотреть отчёт, список техники для новичков или полный инвентарь. Для выхода выберите `0`.

Для электросамоката и электровелосипеда расход энергии вводится в кВт·ч за сутки. У велосипеда расход равен нулю. При добавлении транспорта ответ «техосмотр пройден» задаётся для демонстрации решения сервисного центра; в реальном приложении этот признак поступал бы из результатов диагностики.

## Запуск тестов

```bash
dotnet test VyshKat.sln
```

Тесты проверяют принятие и отклонение транспорта, подмену техосмотра через DI, правило для новичков, расчёт энергии, учёт инвентаря, уникальность номера и запрет обхода техосмотра.

## Архитектурные решения и SOLID

- **SRP (единственная ответственность).** `ConsoleMenu` отвечает за ввод и вывод; `FleetService` — за сценарии работы с парком; `FleetInventory` — за хранение объектов и уникальность инвентарных номеров; `ServiceCenter` — за решение по техосмотру.
- **OCP (открытость/закрытость).** Отчёты и фильтр новичков работают через `ITransport`, `IInventoryItem` и `IEnergyConsumer`, а не через проверку конкретного класса. Новая модель транспорта может быть добавлена наследником `TransportBase` без переписывания расчётов и отчётов. Чтобы создавать новый тип через меню, нужно дополнить выбор типа в `ConsoleMenu`.
- **LSP (подстановка Барбары Лисков).** `Scooter`, `Bicycle` и `ElectricBicycle` взаимозаменяемы в сценариях, ожидающих `ITransport`. Велосипед сообщает нулевое энергопотребление, но сохраняет общий контракт.
- **ISP (разделение интерфейсов).** `IInventoryItem` содержит только поля инвентарного учёта, а `IEnergyConsumer` — только суточный расход. Шлем не обязан реализовывать энергетический интерфейс, зарядная станция — обязана.
- **DIP (инверсия зависимостей).** `FleetService` зависит от абстракций `IFleetInventory` и `IServiceCenter`. Реальные реализации регистрируются в `Program.cs`; тесты могут подставить `FakeServiceCenter` без изменения бизнес-кода.

## Обязательные вопросы из задания

**1. Какой принцип SOLID применён наиболее явно?**

Наиболее явно показан DIP: `FleetService` получает `IServiceCenter` через конструктор, поэтому логика учёта не зависит от конкретного способа техосмотра. Пример — конструктор `FleetService` и регистрация зависимостей в `Program.cs`.

**2. Какой принцип сознательно ограничен или почти нарушен?**

OCP ограничен на уровне консольного интерфейса: при добавлении нового вида транспорта нужно добавить вариант в `ConsoleMenu.AddTransport`. Это приемлемый компромисс для небольшого учебного приложения; доменные операции учёта и отчёты от конкретных видов транспорта не зависят.

**3. Что будет при добавлении нового транспорта, сотрудника или склада запчастей?**

Новый транспорт можно реализовать отдельным классом с контрактом `ITransport`; отчёты и расчёт энергии продолжат работать. Сотрудник не должен попадать в `IFleetInventory`, так как сотрудники не являются имуществом на балансе; при необходимости для них следует создать отдельную модель и сервис. Склад запчастей можно представить отдельной сущностью и отдельным сервисом, а инвентаризируемые запчасти — объектами `IInventoryItem`, если они действительно учитываются на балансе.

**4. Какой тест фиксирует решение техосмотра и как подменяется зависимость?**

`AcceptedTransport_IsAddedToFleet`, `RejectedTransport_IsNotAddedToFleet` и `InspectionDependency_IsResolvedFromDiContainer` проверяют оба решения. В `CreateService` регистрируется подделка `FakeServiceCenter` как `IServiceCenter`; тест задаёт результат `true` или `false`. Дополнительно `TransportWithFailedTechnicalInspection_IsRejectedByRealServiceCenter` проверяет реальную реализацию.
